## Running the tests

```sh
./test.sh                     # all suites
./test.sh e2e                 # one suite: server, page, e2e or docs
./test.sh e2e -g Toggle       # extra arguments go to that suite's runner
./test.sh server local_image  # e.g. a cargo test filter
```

You need the [build tools](./development.mdx#requirements) on your `PATH`.
`./test.sh` runs every suite even when one fails, and exits non-zero if any
failed. Run it before every pull request and every release. CI
(`.github/workflows/test.yml`) runs it on Linux and macOS.

## The suites

| Suite    | Where                     | Runner     | What it checks                                                                                                                                                                                                                            |
| -------- | ------------------------- | ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `server` | `src/*_test.rs`, `tests/` | cargo test | The command line and config file, routes, security (token, local files, WebSocket origin), local images, themes, opening the browser, binding ports, and the running binary over HTTP, WebSocket and file watching.                        |
| `page`   | `app/test/`               | Vitest     | The markdown renderer and every plugin, diagrams, the diagram viewer, WebSocket reconnects.                                                                                                                                                 |
| `e2e`    | `e2e/tests/`              | Playwright | The release binary driven as a user drives it — command line, files on disk, printed URLs — with a real browser checking the page: rendering, live reloads, images, themes, flags, process lifecycle, and release consistency.             |

The e2e files:

| File                     | Covers                                                                                     |
| ------------------------ | ------------------------------------------------------------------------------------------ |
| `preview.spec.ts`        | the core loop: opening pages, live edits on disk, images, reconnects                        |
| `ui.spec.ts`             | rendering of `examples/features.md`, diagram errors, themes, large and oddly named files    |
| `page-features.spec.ts`  | GitHub alerts, the front matter panel, Mermaid's last good drawing, viewer and ELK          |
| `flags.spec.ts`          | command-line flags and the config file, by what they change                                 |
| `lifecycle.spec.ts`      | signals, killed servers, reconnects                                                         |
| `distribution.spec.ts`   | release consistency: versions, asset names, and the docs                                    |

The e2e suite builds the release binary first, so it tests what users
download. Every test starts its own server on its own port, so the tests run
in parallel. A failing test attaches the server's log and output and the
browser console to its report.

`distribution.spec.ts` also checks the documentation: every link between the
docs (and from the README to the site) points to a page and heading that
exist. The `docs` suite of `./test.sh` builds the site, which fails on broken
MDX.

## Writing tests

**A test must fail when the feature breaks.** Passing tests for a broken
feature are worse than failing ones. So:

- Look for content that only appears when the feature works, such as a random
  `token()` written into a file, not for something that is always on the
  page.
- Break the feature on purpose (comment out the fix, return early) and check
  that the test fails. Only then rely on it.
- Don't retry: Playwright's `retries` is 0, because a retry that passes hides
  an intermittent bug.

An e2e test starts a server and opens its page in a browser:

```ts
import { expect, preview, test, token } from "../lib/test";

test("editing the file updates the page", async ({ launch, page }) => {
  const server = await launch();
  server.write("note.md", "# Title\n");
  await page.goto(server.pageUrl("note.md"));
  const written = token();
  server.write("note.md", `# ${written}\n`);
  await expect(page.locator(".markdown-body")).toContainText(written);
});
```

- `test.use({ config: { theme: "dark" } })` writes a config file in the
  server's directory before it starts.
- `launch()` starts another server in a fresh temp root, e.g. with different
  flags or files.
- `server.write(path, content)` creates a file in the server's root and
  returns its path.
- `server.url` is the first URL the server printed on stdout.

Server tests use `App` fixtures from `src/server_test.rs` and `TempDir` for
files.

## Skipped tests and known bugs

A test for a known bug is marked as an expected failure (`test.fail` in e2e,
`test.fails` in the page tests, `#[ignore]` in the server tests) with the
reason. It starts failing when the bug is fixed; then remove the mark.
`cargo test -- --include-ignored` runs the ignored server tests.

## Manual checks

Not covered by the tests, so check by hand before a release:

- Windows: opening the browser and the whole e2e suite.
- WSL: opening the browser (`wslview`, `cmd.exe`, `xdg-open`).
- The release workflow's Linux arm64 and FreeBSD builds, which only run on a
  tag.
- The browser opened by the system, with your own configuration.
- PlantUML diagrams, which are drawn by a remote server.
